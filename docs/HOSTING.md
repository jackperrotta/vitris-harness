# Optional hosting and backend

Static authoring and preview work without a backend origin. A new blank site has no beacon, cookie-compliance page, or localhost API dependency. A `data-lead-form` requires an explicitly configured forms backend; building without one fails clearly. Existing sites with a configured backend origin retain form and analytics behavior.

`@vitris/harness/hosting` exposes `prepareVerifiedRelease` and `deployVerifiedArtifact`. Preparation runs the existing build and gate verification, copies the exact checked bytes into a digest-named local release bundle, and records source, compiler, harness, policy, and bundle identities. Deployment rejects changed source or bundle bytes. The Cloudflare Pages adapter uploads the staged bundle. The CLI `vitris deploy --provider cloudflare` uses that path and runs a remote smoke check. This repository has not deployed a live service during this implementation.

Hosting adapters may supply preview deployment, publication, status, domain attachment, and rollback. The current Cloudflare Pages adapter implements preview deployment and publication. Status, domain attachment, and rollback remain integration work. The existing Worker remains supported for its configured tenants and resources; its GitHub-source preview compiler parity is not yet established for sites pinned to another harness version. Do not treat that preview as proof of a checked local release bundle.

`examples/hosted-integration/` shows a Node-only tenant wrapper with durable job status/events, deterministic local executor, agent handoff, cancellation, resumption, and release preparation. The deterministic executor is a mock. The example does not provide Chairside authentication or operational records, and its `x-demo-tenant` header is not production authentication. Publishing credentials must stay in a separate service.
